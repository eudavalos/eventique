## 🧭 RESUMEN EJECUTIVO

Eventique es una plataforma multi-tenant de invitaciones digitales con arquitectura React + FastAPI + SQLite. El producto presenta un diseño visual elegante y una premisa sólida, pero se identificaron **31 hallazgos críticos** distribuidos en seguridad, funcionalidad, UX, UI, accesibilidad y contenido. Los problemas más graves son de naturaleza **funcional y de seguridad**: un bug de routing hace que todos los RSVP se registren en el evento `default` en lugar del evento correcto; la API expone tokens de admin en texto plano; y se aceptan payloads XSS sin sanitización. Adicionalmente, las **20 imágenes de la invitación están completamente rotas** (apuntan a `/photos/` en vez de `/uploads/`), destruyendo la experiencia emocional que es el core del producto. La plataforma requiere correcciones inmediatas antes de cualquier lanzamiento real.

### H-001 — BUG CRÍTICO: RSVP se registra en evento incorrecto
| Campo | Detalle |
|---|---|
| **Tipo** | Funcional / QA |
| **Severidad** | 🔴 Crítico |
| **Prioridad** | P0 — Inmediato |
| **Impacto usuario** | El invitado confirma asistencia pero el dato no llega al organizador del evento correcto |
| **Impacto negocio** | Pérdida total de datos RSVP — el organizador no puede gestionar confirmaciones |

**Descripción:** El endpoint `POST /api/rsvp` ignora el campo `event_slug` en el body y asigna todos los RSVPs al evento con slug `default` (ID=1). Se verificó: se envió `{"event_slug": "boda-conce-eume", ...}` y el registro apareció en `GET /api/events/default/rsvp`. El endpoint slug-specific `POST /api/events/{slug}/rsvp` no existe o no es el que usa el frontend.

**Recomendación:** 
1. Corregir el backend: el endpoint `/api/rsvp` debe extraer `event_slug` del body y asociar el RSVP al evento correcto.
2. Alternativamente, refactorizar el frontend para usar `POST /api/events/{slug}/rsvp`.
3. Añadir un test de integración que verifique el slug del evento en la respuesta de creación.
4. Migrar los RSVPs mal guardados en `default` hacia el evento correspondiente.

**Justificación:** Este es el flujo más crítico del negocio. Sin RSVPs correctos, la plataforma carece de valor funcional.

### H-002 — SEGURIDAD CRÍTICA: API expone admin tokens en texto plano
| Campo | Detalle |
|---|---|
| **Tipo** | Seguridad / QA |
| **Severidad** | 🔴 Crítico |
| **Prioridad** | P0 — Inmediato |
| **Impacto usuario** | Cualquier superadmin puede ver y usar los tokens de todos los eventos |
| **Impacto negocio** | Violación de confidencialidad; cualquier persona con el superadmin token puede impersonar a cualquier event admin |

**Descripción:** `GET /api/events` (autenticado con superadmin token) devuelve el campo `admin_token` en texto plano para todos los eventos. Ejemplo de respuesta: `{"admin_token": "token-boda-concepcion-eumelio", ...}`. Esto viola el principio de mínimo privilegio: el superadmin no necesita ver los tokens de cada evento, solo gestionarlos.

**Recomendación:**
1. Eliminar `admin_token` de la respuesta del listado de eventos.
2. Hashear los tokens en la base de datos (bcrypt/argon2) — nunca almacenar en texto plano.
3. Crear un endpoint separado `POST /api/events/{slug}/rotate-token` para regenerar tokens.
4. Implementar auditoría de accesos a tokens.

**Justificación:** OWASP Top 10 — A02:2021 Cryptographic Failures. Tokens en texto plano son una vulnerabilidad de seguridad de nivel alto.

### H-003 — SEGURIDAD CRÍTICA: XSS — API acepta HTML/scripts sin sanitización
| Campo | Detalle |
|---|---|
| **Tipo** | Seguridad / QA |
| **Severidad** | 🔴 Crítico |
| **Prioridad** | P0 — Inmediato |
| **Impacto usuario** | Si el admin muestra RSVPs en el panel, scripts maliciosos pueden ejecutarse |
| **Impacto negocio** | Riesgo de XSS stored que puede comprometer el panel admin |

**Descripción:** Se envió `name: "<script>alert(1)</script>XSS Test"` via `POST /api/rsvp` y fue aceptado y almacenado sin sanitización. El servidor respondió con el payload intacto: `{"name":"<script>alert(1)</script>XSS Test",...}`.

**Recomendación:**
1. Sanitizar todos los inputs de texto en el backend antes de almacenar (usar `bleach` en Python).
2. En el frontend React, nunca usar `dangerouslySetInnerHTML` con datos de usuarios.
3. Implementar validación con Pydantic para rechazar HTML en campos de texto.
4. Añadir Content-Security-Policy headers en nginx.

**Justificación:** OWASP Top 10 — A03:2021 Injection. XSS stored en una aplicación multi-tenant puede comprometer múltiples eventos.

### H-004 — BUG CRÍTICO: 20 imágenes rotas en toda la invitación
| Campo | Detalle |
|---|---|
| **Tipo** | Funcional / UI |
| **Severidad** | 🔴 Crítico |
| **Prioridad** | P0 — Inmediato |
| **Impacto usuario** | La invitación muestra solo alt-text en lugar de fotos — experiencia visual completamente dañada |
| **Impacto negocio** | Destruye la propuesta de valor emocional del producto |

**Descripción:** Las **20 imágenes** de la invitación apuntan a `https://eventique.tecnopowerpy.top/photos/story-1.jpg`, `photos/ceremony-venue.jpg`, etc. La ruta `/photos/` no existe en el servidor. Según la arquitectura, los archivos deberían estar en `/uploads/{slug}/`. Ninguna imagen carga — ni las de la historia, los recintos, los cortejo, ni la galería.

**Recomendación:**
1. Mover/servir los archivos de demo en `/uploads/boda-conce-eume/` o configurar nginx para servir `/photos/` → `/uploads/default/`.
2. Actualizar las URLs de imagen en `wedding.ts` (defaults) para apuntar a la ruta correcta `/uploads/{slug}/`.
3. En el `mergeConfig()`, verificar que las URLs de imagen se resuelven antes de renderizar.
4. Implementar un fallback visual elegante (placeholder con gradiente o inicial del nombre) cuando una imagen no carga, en lugar de mostrar broken alt-text.
5. Usar `onError` en los `<img>` tags para detectar y manejar imágenes rotas en producción.

**Justificación:** Sin imágenes, el producto no cumple su función principal. Es la falla de mayor visibilidad para el usuario final.

### H-008 — BUG ALTO: Sin rate limiting en el endpoint RSVP
| Campo | Detalle |
|---|---|
| **Tipo** | Seguridad / QA |
| **Severidad** | 🟠 Alto |
| **Prioridad** | P1 |
| **Impacto usuario** | Un bot puede llenar la BD con miles de RSVPs falsos |
| **Impacto negocio** | Datos de asistencia corruptos; potencial denegación de servicio |

**Descripción:** Se enviaron múltiples RSVPs con el mismo email y con datos inválidos sin ningún bloqueo o throttling. El endpoint acepta cualquier cantidad de requests sin limitación. `guest_count` enviado como `9999` fue silenciosamente cambiado a `1` (existe validación implícita), pero el mensaje de error tampoco se comunica al cliente.

**Recomendación:**
1. Implementar rate limiting por IP: máximo 3 RSVPs por IP por hora (usando `slowapi` o middleware de nginx).
2. Implementar rate limiting por email: 1 RSVP por email por evento.
3. Añadir CAPTCHA o Turnstile en el formulario RSVP para eventos con muchos invitados.
4. Documentar explícitamente los límites de `guest_count` en la validación Pydantic y devolver error claro.
5. Monitorear volumen de RSVPs con alertas automáticas.

### H-009 — BUG ALTO: Sin validación frontend al enviar RSVP vacío
| Campo | Detalle |

3. Deshabilitar el botón Continuar visualmente hasta que los campos estén completos (con `disabled` + estado visual).

### H-010 — BUG ALTO: Labels de formulario RSVP sin atributo `for`
| Campo | Detalle |
|---|---|
| **Tipo** | Accesibilidad / QA |
| **Severidad** | 🟠 Alto |
| **Prioridad** | P1 |
| **Impacto usuario** | Usuarios con lectores de pantalla no pueden identificar qué campo corresponde a cada label |
| **Impacto negocio** | Incumplimiento WCAG 2.1 AA — potencial barrera legal en algunos mercados |

**Descripción:** Los `<label>` del formulario RSVP tienen `htmlFor=""` (vacío). Los inputs tampoco tienen `id`. Esto rompe la asociación semántica label-input. Verificado: `labelData: [{forAttr:"", text:"Nombre completo *"}, {forAttr:"", text:"Correo electrónico *"}]`.

**Recomendación:**
1. Asignar IDs únicos a cada input: `id="rsvp-name"`, `id="rsvp-email"`.
2. Vincular labels: `htmlFor="rsvp-name"`, `htmlFor="rsvp-email"`.
3. Agregar `aria-required="true"` en cada input requerido.
4. Auditar todos los formularios del admin panel con la misma corrección.

Al navegar rápidamente, se observa que secciones enteras están casi invisibles (20-30% de opacidad) mientras el usuario ya las está leyendo. El threshold de IntersectionObserver parece ser muy alto, causando que la animación se active tarde.

**Recomendación:**
1. Reducir el threshold de IntersectionObserver a `0.1` para que las animaciones inicien antes de que el elemento esté completamente en viewport.
2. Reducir la duración de las animaciones de 1000ms a 400-600ms.
3. Respetar `prefers-reduced-motion`: si el usuario prefiere menos movimiento, desactivar todas las animaciones.
4. Asegurar que el contenido sea legible aunque JavaScript falle o sea lento.
